# Java 项目约定

## 输入与边界

先确定仓库根目录、目标模块和变更类型，再定位仓库级指令、构建文件、格式化或静态检查配置、同类实现及测试。不得预设框架、分层名称、统一返回类型或持久化方案。

## 工作流

1. 检查工作树、Java 版本、构建工具、模块依赖和目标目录，使用精确类名或方法名定位后只读取必要源码。
2. 从项目规则与同类实现中识别包结构、层次职责、命名、异常、事务、校验、日志、注释语言和可见性约定。
3. 优先使用项目已有格式化、静态检查和代码生成机制；没有自动化配置时沿用目标文件风格，不批量格式化无关代码。
4. 在保持公开契约和模块边界的前提下完成修改；结构性问题应按任务范围重构，不用重复分支或临时兼容逻辑掩盖。
5. 只在项目约定要求或复杂原因需要说明时添加注释，解释业务原因、边界或风险，不逐行复述代码。
6. 运行受影响模块的编译、静态检查和测试，并审查差异中的越层依赖、无关格式变化、重复基础类型和未覆盖异常分支。

## 缺失约定

项目没有明确约定时，优先保持相邻代码的一致性。若选择会新增依赖、改变公共 API、异常语义、事务边界或模块方向，必须先询问，不能自行建立新的全仓标准。

## 组合与交付

- 涉及数据库结构或 ORM 映射时，组合使用 `common-db`。
- 需要标准 CRUD 骨架时，组合使用 `common-crud`。
- 交付时列出受影响模块、沿用的项目约定、已执行检查及未验证项。
